# 研究 D：软件原生视频生成的先例与技术积木

日期：2026-10-22
任务：为「创造一个不靠大算力、像普通软件一样运行的全新视频生成模型」找地基。核心假设：视频不由神经网络逐像素合成，而是由程序像游戏引擎/动画软件一样「执行渲染」出来。
证据分级：A = 官方文档/官方产品页/论文原文/repo；B = 可信二手报道或官方转述；C = 社区经验/推算。关键结论只用 A 级证据支撑。

---

## 0. 总结论（先说答案）

拼图的大部分积木都现成存在，且每一块都有「在老硬件/手机上实时运行」的实证：

- 傀儡资产与实时渲染：Live2D / Spine / Rive / Lottie，成本模型清晰、运行时开源或可编程调用，980 Ti 甚至普通手机都远超其需求。
- 代码即动画：Manim / Remotion / Motion Canvas 已证明「程序文本 -> 视频」的完整链路；且已有论文证明 LLM 写动画程序 + 渲染回路自纠错在数学动画域可达 94% 渲染成功率。
- 液态角色：2D SDF + smooth-union（metaball 融合）是 ShaderToy 级别的成熟技术，逐像素成本极低，天然适合「液态墨水」形态——形体即公式，不需要骨骼。
- 物理：Verlet/PBD/弹簧质点从 2001 年起就是游戏实时技术，2006 年的硬件就能以 380 fps 跑布料场景；LiquidFun 在浏览器和手机上实时跑流体粒子。
- 文生动画的商业验证：Vyond Go（ChatGPT 驱动）已经在卖「提示词 -> 模板傀儡动画」，证明「语言模型当导演 + 傀儡执行」这条产品路线成立——但它封闭、模板化、只做双人对话和讲解头。

真正的空白（没人做过的部分）有三处，全部不在渲染层，而在「导演层」和「资产层」：

1. 面向叙事表演（不是数学讲解）的 LLM 导演：让语言模型输出受约束的动画程序（DSL 时间轴），并能对喜剧节奏、走位、表情表演负责，带渲染-看片-改稿的反馈回路。现有工作只做到数学场景（Manim 系）和模板讲解（Vyond Go）。
2. SDF 液态角色作为一等傀儡资产：SDF 演示满地都是，傀儡系统满地都是，但没有一个现成系统把「SDF 软体角色」做成可被时间轴/参数驱动的标准资产格式，与图层傀儡混编在同一场景里。
3. 非人形、无骨骼拓扑角色的单图自动建傀儡：自动绑骨/自动分层研究全部预设「人形骨骼」或「动漫人体分层」。一只没有固定拓扑、靠融合变形运动的液态狗，没有现成自动管线。

最大技术风险：不在算力，在导演层的表达可靠性——生成的动画程序能不能真的「演得好看、节奏对、笑点成立」。次级风险是单图自动分层的质量上限（最新研究 Bunraku 的定量结论：端到端误差主要来自分解，不是运动）。

## 1. 模板傀儡式文生动画：Vyond / Adobe Character Animator / Cartoon Animator

共同模式（三家完全一致）：预制角色资产 + 绑定（rig）+ 动作/表情库 + 时间轴数据，运行时只做 2D 合成渲染。因此渲染成本与「视频生成」无关，是普通软件成本。差异只在自动化程度和开放性。

### 1.1 Vyond（原 GoAnimate）

- 工作方式（证据 A，官方帮助文档）：Vyond Go 提供 Text to video：输入提示词由 AI（官方博客明示 powered by ChatGPT）生成脚本，再套模板生成视频；Script-to-video 把用户脚本灌进选定的布局模板。官方帮助文档明确写死限制：脚本转视频只支持单人（Talking Head / Narration 布局）或最多双人对话（Conversation 布局），脚本里多余的角色和画面描述「不会被考虑」。
- 资产模式（证据 B，维基/产品资料）：数万个预制动画资产（角色、动作、模板、道具、音效），拖拽组合，角色可自动对口型，导出 MP4/GIF。
- 自动化程度判定：导演层已被 LLM 接管（写脚本、选模板），执行层全是模板槽位填充。开放性：零。没有公开 API 让外部程序驱动其傀儡系统，模板之外无表达力。
- 对我们的意义：商业上验证了「LLM 导演 + 傀儡执行」；同时划出了它的天花板——模板槽位只能装讲解和对话，装不下叙事表演。这正是空白点 1 的位置。

### 1.2 Adobe Character Animator

- 工作方式（证据 A，Adobe 官方产品页）：分层 PSD/AI 图稿导入后即成 puppet；用摄像头和麦克风实时驱动——自动口型（lip sync）、面部与身体追踪；Triggers 把预设动作/表情切换绑到按键；还有 Puppet Maker 模板定制和行为（behaviors，如物理、行走）。
- 自动化程度判定：它是「真人表演 -> 傀儡」的实时转译器，导演是人。绑定仍需按图层命名规范人工准备。但它证明了两件事：(1) 傀儡的驱动信号可以是一组低维参数流（面部追踪点、音频 viseme、触发开关），完全可以由程序而非真人产生；(2) 音频 -> viseme 口型是现成算法，台词驱动口型不需要神经视频模型。
- 对我们的意义：参数流驱动 + 触发器动作库，就是 DSL 时间轴需要输出的信号格式的现成参照。

### 1.3 Reallusion Cartoon Animator 5（CTA5）

- 工作方式（证据 A，Reallusion 官方发布稿/Cartoon Brew 报道）：任何位图/矢量图可导入、绑定、动画化；Spring 弹簧物理自动生成次级动作（secondary motion）；Free Form Deformation（FFD）做卡通夸张；360 Head Creator 把 2D 头做成可 0-360 度转头；PSD 管线、矢量（SVG）管线、动作库、面部 mocap、音频自动口型、3D 动作转 2D。
- 自动化程度判定：三家中对「任意单图入场」走得最远：自动绑骨（auto rigging，社区评价为快但需人工修）、弹簧与 FFD 把「逐帧画变形」变成参数。仍然是 GUI 工具、无程序化导演接口。
- 对我们的意义：CTA5 的弹簧次级动作 + FFD 证明「夸张变形」在傀儡范式内是参数问题，不是逐帧问题——这对墨团团的 squash & stretch 至关重要。

### 1.4 本节小结

| 维度 | Vyond | Character Animator | Cartoon Animator 5 |
|---|---|---|---|
| 导演 | LLM（封闭模板） | 真人表演 | 真人操作 |
| 资产 | 平台预制库 | 分层图稿自备 | 任意单图 + 预制库 |
| 驱动信号 | 脚本/模板 | 参数流 + 触发器 | 时间轴 + 物理参数 |
| 程序可调用 | 无 | 无公开 API | 无公开 API |
| 渲染成本 | 普通软件级 | 实时 | 实时 |

结论：范式成熟、产品成熟，但三家全部是「给人用的工具」，没有一家把导演层开放给程序。把导演层换成我们自己的 LLM + DSL，是产品形态上的真空地带。

## 2. 实时傀儡运行时：Live2D / Spine / Rive / Lottie

这一节回答：渲染成本有多低、可编程性有多强。四者都是「资产文件（网格/矢量 + 参数/骨骼 + 动画数据）+ 轻量运行时」的结构，逐帧计算量是顶点变换和混合，不是像素合成。

### 2.1 Live2D Cubism

- 机制（证据 A，Live2D 官方手册）：原画切分为 ArtMesh（带网格的图层件），用参数（parameter）驱动变形器（deformer）与关键形态（keyform）做多路混合；.moc3 模型 + 纹理 + .model3.json（动作/表情清单）即完整资产。
- 成本模型（证据 A，官方 Performance 页）：官方逐项列明成本动因——ArtMesh 数量、多边形数、变形器数量与层级、单个对象上挂的参数数量（影响最大，参数混合计算随乘法增长，官方建议单对象不超过 2 个参数设置）。即：成本是可预算、可审计的，几十到几百个 ArtMesh 的模型在手机上跑 VTuber 是日常（VTube Studio 生态）。
- 可编程性：Cubism SDK（C++/C#/Java/JS 等）可在代码里逐帧 setParameterValue 驱动任意参数，动作/表情以文件形式触发。参数接口就是为「外部信号驱动」设计的——面捕软件如此，我们的 DSL 时间轴同样如此。
- 许可注意：SDK 使用受 Live2D 许可约束（发布有条件），自研系统若商用需评估，或只借鉴其参数混合模型、用自有运行时实现。

### 2.2 Spine（Esoteric Software）

- 机制（证据 A，官网）：2D 骨骼动画专用：骨骼层级 + 网格蒙皮权重 + IK/路径/物理约束 + 掺混（mix）动画状态机；编辑器导出骨骼数据（JSON/二进制）+ 图集，官方 runtimes 覆盖几乎所有游戏引擎与语言（C、C++、C#、Unity、Unreal、Web 等），运行时中骨骼可被代码实时操纵（设骨骼位置、换装 skins、附件切换、事件回调）。
- 成本：游戏级。骨骼数十根、网格顶点数百量级的角色，在十多年前的移动设备上批量同屏是常态；成本动因是骨骼数、顶点数、约束数（社区优化文献亦如此归纳，证据 C）。
- 可编程性：四者中最强、最「引擎化」——它本来就是给程序员集成的。动画状态机、掺混、事件、代码直接改骨骼，DSL 编译目标选它最顺手。
- 许可注意：runtimes 可免费集成，但使用者须持有 Spine 编辑器许可证（官方 runtime 许可条款）。

### 2.3 Rive

- 机制（证据 A，Rive 官方）：矢量图形 + 状态机（State Machine）：输入（Boolean/Number/Trigger）驱动状态转移与混合，动画逻辑内置在 .riv 二进制文件里；运行时开源。
- 成本（证据 A，Rive 官方 Renderer 介绍）：自研 Rive Renderer 主打解析式抗锯齿矢量渲染，官方称可让全屏矢量内容以 120 fps 动起来，且「不需要新硬件」；.riv 文件比视频/GIF/图片序列/JSON 格式小一个量级。Web 运行时包体 222KB-648KB 量级（官方文档数据）。
- 可编程性：状态机输入即 API——程序只需在对的时刻给对的输入，角色自己完成状态转移与混合。这是四者里最接近「动画即软件逻辑」的范式：行为被编译进资产，导演只发事件。
- 对我们的意义：如果要选一个现成运行时做渲染层，Rive 的「状态机资产 + 输入驱动」与 DSL 导演的契合度最高；且运行时开源（MIT 系），许可干净。

### 2.4 Lottie

- 机制（证据 A，Airbnb 官方工程博客）：After Effects 动画经 Bodymovin 导出为 JSON，运行时在移动/Web 端原生实时渲染矢量动画；文件极小（官方对比：GIF 是其 2 倍以上，PNG 序列是其 30-50 倍）；运行时可改颜色、位置等任意可动画属性，可交互擦洗（scrub）进度。
- 局限：本质是线性时间轴的矢量关键帧回放，没有状态机、没有骨骼/物理，复杂角色表演表达力最弱；适合图标与简单图形动画，不适合当角色引擎。
- 对我们的意义：证明「JSON 即动画、运行时渲染」这条分发链路的极致轻量；可作简单道具/UI 动效层，不作主角层。

### 2.5 本节小结

渲染层结论：现成、便宜、可编程。980 Ti 对这些运行时是杀鸡用牛刀——它们的设计目标硬件是手机和浏览器。选型建议：主角层借鉴 Spine 的骨骼/网格/状态机模型或直接用 Rive 运行时；不要自研渲染器，渲染不是创新点也不是风险点。

## 3. 代码即动画：Manim / Motion Canvas / Remotion / p5.js

这一节回答：「文本/代码编译成动画」的链路是否完整、LLM 写这种代码靠不靠谱。

### 3.1 四个系统的链路

- Manim（证据 A，官方文档）：Python 类即 Scene，construct() 里用代码摆对象、play() 动画；命令行渲染出 MP4。渲染器为 Cairo（软件光栅）或 OpenGL。3Blue1Brown 的全部数学视频就是这条链路的产品——证明「程序文本」可以承载完整叙事节奏的动画，只是领域是数学图形。
- Motion Canvas（证据 A/B，官方与 Remotion 官方对比页）：TypeScript，生成器函数（generator）写程序化时间轴，配套实时预览编辑器；只能渲染 Canvas 内容。与 Remotion 的区别被官方概括为：Remotion 是声明式（给定帧号算出画面），Motion Canvas 是命令式/程序式（按时间轴顺序推进）。
- Remotion（证据 A，官方文档 The core idea）：「视频是随时间变化的图像函数」——React 组件以 useCurrentFrame() 为输入算出每一帧，渲染时逐帧截图加 ffmpeg 合成。成本提示：它走浏览器光栅化，逐帧截图的吞吐远低于游戏引擎式直接渲染；胜在生态（React/CSS/现成组件）。对老硬件离线出片可用，但不是最省的执行方式。
- p5.js / Processing（证据 B，通行事实）：draw() 循环即动画，创意编码生态二十余年；可录屏/逐帧导出成片。表达力靠手写代码，无时间轴抽象，适合作原型验证工具，不适合作产品运行时。

共同点：四者都证明了「动画 = 可执行文本」在工程上毫无神秘之处；LLM 最擅长生成的恰好是文本/代码。这就是导演层选「写程序」而不是「出像素」的根本原因。

### 3.2 LLM 写动画程序的实证（关键证据）

- Manimator（证据 A，arXiv 论文）：三段管线——LLM 把输入（提示词/论文）写成结构化场景描述，第二只代码 LLM 把描述翻译成 Manim 代码，渲染出片。架构上与「导演 LLM 写 DSL、引擎执行」完全同构，只是中间表示是 Manim 代码。
- ManimTrainer / ManimAgent 研究（证据 A，arXiv 论文）：系统研究 LLM 生成 Manim 动画：17 个 30B 以下开源模型、ManimBench 基准；关键方法 Renderer-in-the-loop（RITL，渲染结果回喂模型自纠错）与文档增强版 RITL-DOC；最佳组合渲染成功率（RSR）94%、与参考视频视觉相似度 85.7%。结论意义：(1) 让 LLM 直接写通用代码（Manim/Python）裸跑成功率不够，但「渲染-检查-改稿」回路 + API 文档注入能把可靠性推到产品可用区；(2) 这套方法论只在数学动画上验证过，叙事角色表演域是空白（见第 7 节）。
- Generative Manim 等开源工具（证据 B）：GPT 生成 Manim 代码在线出片，已产品化小工具形态。

### 3.3 对我们的设计含义

- 不要让 LLM 写图灵完备的通用代码（Manim/Python/JS）：可靠性随自由度下降，且无法做静态校验。应让它写受约束的 DSL：一组有限动词（入场/走位/动作原语/表情/镜头/台词/物理开关）、强类型参数、时间轴结构固定。DSL 可在执行前做完整校验（资产存在性、参数范围、时序冲突），错了打回重写——这是通用代码路线做不到的。
- 渲染回路必须内置：出片后抽帧/整片回喂视觉模型做「导演自检」（角色出画没、动作对没、节奏拖没），按检查单改稿。Manim 系论文证明回路价值，我们把它从「查代码错误」升级为「查表演质量」——这一步没人做过。

## 4. 数学形状渲染：SDF / 隐函数 / metaballs 与液态角色

### 4.1 技术事实

- SDF（符号距离场）：形状不存顶点，存一个函数 f(p) = 到表面的符号距离。圆、胶囊、圆角矩形等基元都有解析式；组合靠算子：并集 min、交集 max、差集，以及关键武器 smooth-min（smin）。
- smooth-union / metaball 融合（证据 A，Inigo Quilez 官方文章）：smin 把两个形状在靠近时像黏液一样融出桥联，k 参数控制融合半径——「如黏土般雕刻有机形状」。iq 用它在 Shadertoy 里实时雕出人脸等有机形体；其 SDF 作品自 2008 年起就是 4KB 级别 demo 的内容。
- 2D 与 3D 的成本分野（关键）：3D SDF 要 raymarching（逐像素迭代步进），2D SDF 不用——每个像素只需对少量基元求值、取 smin、按距离做抗锯齿着色即可，是单个 fragment shader 里几十行算术。980 Ti 跑全屏 2D SDF 是 trivial 级别；甚至可以退到 CPU 用 marching squares 提轮廓再矢量光栅，连 GPU 都不依赖。

### 4.2 对「液态墨水角色」的可行性判定：高度对口

墨团团的形态学本质：无固定拓扑、靠融合/分离/拉伸运动、表面是流体。这恰好是骨骼/网格范式的死穴、SDF 的主场：

- 身体 = 一组 2D SDF 基元（主团 + 可分裂子团）的 smin 融合体；「变形」= 基元位置/半径/拉伸参数随时间变化 + 域噪声扭曲（domain warp）制造墨流动感。分裂、合并、拉丝、摊饼、弹回，全是 smin 场的自然行为，不需要逐帧画。
- k（融合度）= 「墨的黏稠度」，是可动画参数：受惊时 k 变小散成多团，安心时融回一团——物理感和表演由同一个参数承载。
- 五官与配件（眼睛、铃铛）不进 SDF：作为图层件锚定在场的等值面/势场方向上随形变漂移（铃铛再挂弹簧，见第 6 节）。这是 SDF 层与傀儡层的混合点，现成系统里没有（空白点 2）。
- 墨迹纹理：SDF 只给形状不给质感。解法是程序纹理——在场空间里采样 fBM 噪声做内部墨纹/边缘晕染（iq 的 fBM-SDF 文章即此路，证据 A），或把静态墨纹贴图按场坐标扭曲采样。质感上限是本路线的主要审美风险（见第 8 节）。

### 4.3 判定

现成可用：2D SDF 基元库、smin 融合、域扭曲、程序墨纹，全部 ShaderToy 级代码量，无专利与许可负担，无算力门槛。需要自研的是「SDF 角色资产格式」（基元组 + 参数轨道 + 五官锚点规范）与它和傀儡时间轴的混编执行。

## 5. 自动绑骨 / 自动分层：从单张角色图生成可动傀儡

这是资产层的核心问题：用户给一张角色设定图，系统要自动得到可动资产。此节逐项核查成熟度。

### 5.1 Animated Drawings（Meta FAIR）——人形 2D 的现成基线

- 方法（证据 A，论文 A Method for Animating Children's Drawings of the Human Figure, ACM TOG 2023；开源 repo）：检测（Detectron2 分割角色）+ 姿态估计给关节点 -> 生成三角网格 -> BVH 动捕数据（Mixamo/CMU）经 Retargeter 重定向 -> ARAP（As-Rigid-As-Possible）变形逐帧驱动网格。repo 支持用 YAML 配置自定义骨骼（官方示例含四条腿、六只臂的非标角色）、多角色、背景、导出 MP4/GIF、无头渲染。
- 成熟度：研究级可用产品（官方在线 demo 多年运行）。硬限制写在方法里：预设人形骨骼、肢体不得重叠、自动关节点常需人工在修正界面里拖正。算力：检测/姿态是小模型推理，一次性的资产构建成本，CPU/小 GPU 均可，摊到每集为零。
- 对我们的定位：访客角色（人形战士等）的自动建傀儡基线可直接站在它肩上；其「配置自定义骨骼」机制也给了非人形角色一条半自动路（人工标一次骨骼，永久复用）。

### 5.2 See-through 与 Bunraku——单图自动分层的最新进展（2025-2026）

- See-through（证据 A，arXiv 论文 Single-image Layer Decomposition for Anime Characters）：把一张动漫角色图分解为分层 RGBA 部件（含被遮挡部分的补全 inpainting）+ 伪深度排序；产物可导出分层 PSD，论文称职业动画师评价「基本可直接用于生产、只需少量修改」；接回 Animated Drawings 管线后，大变形下遮挡关系明显优于原版（裙-鞋-发的分层不撕裂）；头发用弹簧物理实时驱动；还做了实时 VTuber 说话头。
- Bunraku（证据 A，arXiv 论文 Turning a Single Illustration into an Editable Live2D Character）：单图 -> 可编辑 Live2D 角色的完整管线。其定量结论对我们最重要：在有画师真值绑定的角色上对比，端到端保真度差距「主要来自分解（切层边界与遮挡补全），不是运动预测」——即资产层的瓶颈定位被实证为分层质量，运动层反而已经够好。
- 算力定位：这类分解用扩散/大模型做一次性推断，成本在资产构建期（云端跑一次都可接受），运行时零成本。注意其训练域是动漫人体，对非人形/水墨风角色的迁移性未验证。

### 5.3 Layered Neural Atlases 与 CoDeF——「规范图集 + 变形场」分解范式

- Layered Neural Atlases（证据 A，ACM TOG 2021）：把一段视频逐视频优化分解为分层 2D 图集（每个物体一张统一外观图）+ 每像素到图集的映射与 alpha；编辑图集一处、全片自动一致地改。成本：逐视频 MLP 优化，小时级、需 GPU——它不是生成工具，是分解/编辑工具。
- CoDeF（证据 A，CVPR 2024）：视频 = 规范内容场（canonical image）+ 时序变形场；逐视频联合优化；能把图像算法「抬升」为视频算法（只处理规范图一张，变形场传播到全片），且能跟踪水、烟等非刚体。
- 对我们的意义：这两者从研究侧证明了同一个因子分解——「一份静态资产 + 一个变形/参数场 = 整段视频」——正是软件原生生成的数学骨架（傀儡资产 = 规范表示，时间轴参数 = 变形场）。区别在于：他们用逐视频优化求变形场（贵、事后），我们用导演程序直接写变形场（免费、事前）。范式成立已被证明，我们要做的是把它从「拟合已有视频」翻转为「合成新视频」。

### 5.4 3D 侧参照：UniRig 等

- UniRig（证据 A，SIGGRAPH 2025 / 官方 repo）：自回归大模型 + 骨点交叉注意力，一次预测任意 3D 模型的骨骼树与蒙皮权重，Rig-XL 1.4 万模型数据集；repo 要求 8GB 以上显存 GPU。证明「自动绑骨」在 3D 已进入大模型时代，但对 2D 傀儡不直接可用，仅作趋势参照。
- CharacterGAN 一类（证据 C）：老一代 GAN 做角色生成/补全，质量与可控性已被扩散时代的分层管线（5.2）超越，不建议作为技术选型依据，仅记录其存在。

### 5.5 本节小结：成熟度地图

| 目标 | 成熟度 | 代表 | 成本位置 |
|---|---|---|---|
| 人形绘画 -> 骨骼傀儡 | 可用（需人工修关节点） | Animated Drawings | 一次性构建 |
| 动漫单图 -> 分层 RGBA 资产 | 研究前沿，接近生产 | See-through / Bunraku | 一次性构建（可云端） |
| 已有视频 -> 图集+变形场分解 | 成熟研究工具 | LNA / CoDeF | 逐视频重优化（不借用其成本，只借用其范式） |
| 任意 3D 模型自动绑骨 | 快速成熟 | UniRig | 一次性构建 |
| 无骨骼液态角色自动建资产 | 空白 | 无 | 需自研（走 SDF 参数拟合，见第 4 节） |

关键设计原则由此确立：把所有「重」计算（检测、分层、补全、拟合）都压到一次性资产构建期，构建完的资产是纯数据（图层/网格/SDF 参数），每集的生成只剩执行渲染——这是「像普通软件一样运行」的结构性保证。

## 6. 物理与粒子：2D 弹簧质点 / 流体在老硬件实时的先例

结论先行：物理是这套系统里最不用担心的一层。全部是 2000 年代的遊戲技術，成本比渲染还低。

### 6.1 Verlet + 约束求解（Jakobsen / PBD 系）

- Advanced Character Physics（证据 A/B，Jakobsen, GDC 2001 / Hitman 引擎）：粒子 + Verlet 积分 + 距离约束迭代松弛，一套机制同时做刚体、布料、毛发、角色骨骼的近似物理。核心优点：无条件稳定、每条约束每帧只有约一次除法量级的计算。
- Position Based Dynamics（证据 A，Müller et al. 2007 论文原文）：直接操作位置解约束；论文结果段给出场景数据——6 个刚体 + 3 块布的场景模拟加渲染超过 380 fps（2006 年硬件）；1364 顶点布料含自碰撞平均 30 fps。同系的 Position Based Fluids（2013）把不可压缩流体也纳入同一求解器。
- Shape Matching（Müller et al. 2005）：无网格变形——粒子云记住原形、每帧求最优刚性拟合再拉回，是「软体但记得自己形状」的标准做法，正是液态角色弹回原形的现成算法（与 SDF 路线互备：SDF 管形状、shape matching 管动力学，或直接用弹簧团簇近似）。

### 6.2 LiquidFun / Box2D（证据 A，Google 官方开源博客与 repo）

Box2D 的官方扩展：加入基于粒子的流体与软体模拟（SPH 类）；平台无关 C++，官方提供 Android/iOS/浏览器（Emscripten 编译成 JS 在网页里跑）版本，并为 ARM 做了 NEON 优化。定位是手机游戏里的实时液体——数千粒子量级在 2013 年的手机上实时。

### 6.3 元胞自动机粒子（Powder Game 系）

- Powder Game（证据 B）：2007 年上线的浏览器玩具，四十余种元素（沙、水、火、风压）在像素网格上按局部规则实时演化，跑在 2007 年的普通电脑浏览器里。后继者 Sandspiel 等延续同一范式。
- 对我们的意义：环境级效果（墨滴飞溅、烟尘、水花、火星）可以用元胞/粒子层廉价生成，不需要逐个建模；这类层与角色层在合成时叠加即可。

### 6.4 本节小结：物理积木清单

| 需求 | 现成方案 | 成本 |
|---|---|---|
| 铃铛穗子/头发/尾巴的次级摆动 | 弹簧链（Verlet 绳） | 可忽略 |
| 卡通 squash & stretch 辅助 | FFD / 弹簧缩放（CTA5 已产品化） | 可忽略 |
| 液态体弹回原形 | Shape Matching 粒子云 | 千粒子级实时 |
| 墨滴/液体粒子 | LiquidFun 式 SPH 粒子 | 千粒子级实时（手机级硬件） |
| 环境粒子（烟/火/尘） | 元胞自动机 / 简单粒子系统 | 网格级实时 |

声音侧附带说明：口型由音频 viseme 驱动是 Character Animator 已产品化的算法；TTS 与音效是管线外组件，不占渲染预算。此处不展开。

## 7. 拼图：哪些现成、哪块是空白

设想系统（与项目架构 v1 对应）：导演层 LLM 把提示词/剧本编译成动画程序（DSL 时间轴）-> 资产层是傀儡（图层/网格/SDF）-> 动作层是参数化原语 + 物理 -> 渲染层是游戏级 2.5D 合成 -> 编码出片；声音与画面共用同一时间轴。

| 层 | 现成可用（直接拿或站在其上） | 成熟度 |
|---|---|---|
| 渲染执行 | Rive 运行时（开源、状态机、120fps 级矢量渲染）；或 Spine 运行时（骨骼/网格/状态机最全，需许可证）；或自研轻量合成器（技术无难度） | 成熟产品 |
| 傀儡资产格式 | Live2D 的参数混合模型、Spine 的骨骼+网格+skin 模型，可借鉴数据结构 | 成熟产品 |
| 代码即动画链路 | Manim/Remotion/Motion Canvas 全链路；LLM 写代码 + RITL 回路方法论 | 成熟 + 论文实证 |
| 液态形体 | 2D SDF + smin 融合 + 域扭曲 + 程序墨纹（ShaderToy 级代码） | 成熟技术 |
| 物理 | Verlet/PBD/弹簧/shape matching/LiquidFun | 二十余年游戏标配 |
| 人形自动建傀儡 | Animated Drawings（开源） | 研究级可用 |
| 动漫自动分层 | See-through / Bunraku（2025-26 论文与代码） | 研究前沿 |
| 因子分解范式 | LNA / CoDeF 证明「规范资产 + 变形场」成立 | 论文实证 |

真正的空白（检索范围内无人做过）：

1. 叙事表演域的 LLM 导演 + 受约束 DSL。现有 LLM 导演只有两类：数学图形（Manim 系，对象是公式和几何体）和模板讲解（Vyond Go，对象是槽位）。没有公开系统让 LLM 用一套为「角色表演」设计的有限动词集（走位、动作原语、表情、反应时序、镜头、物理开关）编排一段有喜剧节奏的叙事动画，并对成片做视觉自检改稿。DSL 的动词集设计（表达力与可校验性的平衡点）本身就是待发明物。
2. SDF 液态角色的傀儡资产标准。SDF 演示是「一个 shader 一幅画」，傀儡系统是「网格 + 参数」；把 SDF 基元组做成可复用、可被时间轴参数驱动、五官配件可锚定、能与图层傀儡同场混编的资产格式与运行时，没有先例。
3. 无骨骼拓扑角色的自动建资产。自动绑骨/分层全预设骨骼或人体分层；对「一张液态角色设定图 -> SDF 基元组 + 锚点」的自动拟合管线是空白（半自动版——人工摆一次基元——立刻可用，全自动版是研究题）。
4. （次级空白）开放的端到端所有权：现有傀儡生态的关键环节或封闭（Vyond/Adobe）或许可受限（Live2D/Spine）。一个从 DSL 到运行时全部自有/开源的栈，是产品空白而非技术空白。

## 8. 最大技术风险（按严重度排序）

1. 导演层的表演可靠性（最大风险）。渲染再快，若 LLM 编排的走位、时序、反应不好笑、没戏，系统一无是处。缓解证据：Manim 域的 RITL 回路把渲染成功率推到 94%——但那是「能跑通」的可靠性，不是「演得好」的可靠性；后者需要视觉自检的评价标准（构图/出画/节奏/表情可读性检查单）与动作原语库的质量下限托底。此风险只能靠原型实测收敛，无法靠调研消除。
2. 单图自动分层的质量上限（资产层风险）。Bunraku 的定量结论：误差主源是分解而非运动。任意画风（尤其水墨、非动漫人体）上自动分层可能达不到生产级，需要保留「人工修一次、永久复用」的半自动通道，并接受首批资产的人工成本。
3. SDF 角色的质感天花板（审美风险）。SDF + 程序噪声的墨感与手绘水墨之间可能存在观感差距；混合路线（SDF 管形、手绘纹理按场坐标采样管质）可缓解，但锚定与拉伸下的纹理稳定性需原型验证。
4. DSL 表达力陷阱（设计风险）。动词太少则剧情装不下（重蹈 Vyond 模板覆辙），太多则 LLM 产出不可靠、校验不住。需要用目标剧集的真实分镜反推最小动词集，而不是先验设计。
5. 许可与生态风险（可控）。Live2D/Spine 的许可条款、Vyond/Adobe 的封闭性——通过「借鉴数据模型 + 自研/开源运行时（Rive 系）」规避，不让核心资产被单一厂商格式锁定。

明确不是风险的：渲染算力（第 2 节）、物理算力（第 6 节）、逐帧成本（全系统最贵的单帧操作仍是普通 2D 合成）、存储与分发（资产是 KB-MB 级数据文件）。
