# Keep a pointed correction scoped

## Test whether the correction is general

- Read the correction in its own words before you act on it.

- Treat a correction as local to the scene, line, clip, image region, or design part it named unless the user said it applies everywhere.

- Ask the user whether a correction is general when the wording could cover one scene or the whole series.

- Do not infer a general rule from a single example, a single clip, or a single line the user rejected.

- Do not infer a general rule from the tone of a correction, because a blunt correction is still a local correction unless the user says otherwise.

## Name the pointed span before you change anything

- Quote the exact correction the user pointed at at the top of your working note.

- List the spans that correction touches and leave every other span out of the list.

- Name the span in the terms of the work, such as lines and beats for a script, a named region or part for an image or design, and seconds and a scene for a video segment.

- Ask the user before you touch a span outside the list.

- Treat a question about a note or an annotation as a question about that note alone and do not rewrite the passage it annotates.

## Change only the listed spans

- Leave every unlisted line word for word as it was in the previous delivered version.

- For image or design work, change only the named region or part and describe every unmentioned region as unchanged, so a correction to one part never redraws another part.

- Do not add a character, an object, a scene, or a line that the user did not ask for in this correction.

- Do not rewrite locked dialogue, reorder beats, or change a passage the user called fine.

- List any knock on change the pointed fix forces as a separate proposed change and wait for approval before you apply it.

- Restore a passage the user says was originally fine instead of keeping a replacement for it.

- Say plainly in your reply that the change is local when you apply a local correction, so the user can see the scope you used.

## Prove the scope before you deliver

- Compare the revised document with the previous delivered version span by span.

- List every changed span before the revised document and check that the list matches the spans named at the start.

- For image or design work, list the changed region beside the regions you left unchanged.

- Check that no locked line changed outside a pointed span and that no new element slipped into an unchanged span.

- Deliver the complete revised document in the same reply as the changed span list.

## Record only what the user made general

- Write a standing rule into memory or a ledger only when the user used general wording or said the point applies generally.

- Quote the user wording that made the rule general beside the rule you record.

- Keep a local correction out of memory, out of a ledger, and out of a skill when no general wording supports it.

- Check an existing standing rule before you reuse it and drop it when its source was one local correction.

- Offer the general version as a question first when you think a local correction might deserve to become general, and wait for the user to approve it.

## Alternatives for better results

- Split a correction that touches several scenes into one local change per scene, so each change can be checked on its own.

- Ask the user to confirm the exact span a correction covers when the correction is ambiguous instead of widening it yourself.

- Keep the corrected version beside the previous version for one round, so a too broad change can be undone without rewriting the whole piece.
